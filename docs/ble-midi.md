# BLE MIDI

The Pipo is a BLE-MIDI 1.0 peripheral. It sends the MIDI generated by the engine to one connected host (macOS, iOS, Windows, Android, a DAW) and receives Program Change messages from it.

The layer is our own code on top of [NimBLE-Arduino](https://github.com/h2zero/NimBLE-Arduino) 2.5.1 (`lib_deps` in `platformio.ini`). It replaced the lathoub BLE-MIDI library, the MIDI Library and the vendored NimBLE 1.4.1, which no longer worked with the Arduino 3.3 core.

| File | Role |
|---|---|
| `src/midi/ble_midi_codec.h` | Packet encoder, packet parser and outbound queue. Pure C++, unit tested in `test/test_ble_midi`. |
| `src/midi/midiBLE.cpp/h` | NimBLE server, connection handling, sender task, inbound Program Change queue. |
| `src/midi/midi_io.cpp` | Calls `MidiBLEsend*()` when `BLEEnabled` is set, next to the USB sends. |

## How a message travels

1. The engine (main loop, Core 1, 400 Hz) calls `midiio.sendControlChange()` and similar, which call `MidiBLEsendCC()` and similar.
2. `MidiBLEsend*()` only puts the message in the outbound queue, under a spinlock held for a few microseconds. It never touches BLE and never blocks, so the 400 Hz loop is unaffected.
3. `bleMidiTask` (Core 0, next to the NimBLE host) wakes once per **connection interval**, takes as many messages as fit in one packet, and sends them as one notification. It sends up to 3 packets per interval when more is queued.
4. The host receives one packet per connection event instead of one per message.

Nothing is queued while no host is connected and subscribed to notifications.

## Sending only as fast as the link allows

A BLE link can only move data at connection events, every 7.5 to 30 ms depending on the host. Producing faster than that doesn't send anything sooner; it only fills NimBLE's buffers, which costs heap and adds latency. So the sender is paced by the link, not by the engine:

- **Pacing:** the sender wakes once per connection interval (rounded up to the next millisecond).
- **Back-pressure:** before each packet it checks NimBLE's free buffer count (`os_msys_num_free()`). With fewer than 8 free buffers, the host is still holding earlier packets because the link is slower than we produce. The sender skips that interval and keeps its batch, and the queue keeps absorbing new values in the meantime.
- **Retry:** if `notify()` fails, the batch is kept and sent at the next interval.

### The outbound queue

The queue (`BleMidiOutQueue`) has two parts, so that a slow link loses old values, never events:

| Messages | Storage | When the link is slow |
|---|---|---|
| **Control Change, Pitch Bend, aftertouch** | 32 "latest value" slots, one per channel + controller (one per channel for Pitch Bend and channel pressure) | A new value overwrites the queued one. Only the most recent value is sent, so there is never a backlog of stale values. |
| **Note On, Note Off, Program Change** | A 32-message FIFO, in order | Kept in order and never merged. |

Each packet takes the FIFO first (notes are timing critical), then the latest values, round-robin so a constantly moving controller can't starve the others.

### Dropping when overloaded

| Situation | What happens |
|---|---|
| FIFO full, new **Note Off** (or Note On with velocity 0) | The oldest queued Note On is evicted and the Note Off is queued, so a note can't hang. An unmatched Note Off for the evicted note is harmless. |
| FIFO full, new Note Off, and the FIFO holds only Note Offs | The new Note Off is dropped. |
| FIFO full, any other new message | The new message is dropped. |
| A Note Off for a note whose last queued event is already a Note Off | Not queued twice. |
| All 32 latest-value slots busy with other controllers, new controller | The new value is dropped. Controllers already queued keep updating. |

Drops are counted and printed when the host disconnects (see [Diagnostics](#diagnostics)).

### What the rest of the firmware must do

- **Control Change and Pitch Bend:** nothing. Sending a value every engine frame is fine; the queue keeps only the latest one. The engine's own deduplication (`MidiTranslator::should_send_cc()`) still saves work.
- **Notes:** avoid bursts of more than about 30 notes within one connection interval (7.5 to 30 ms). Beyond that, Note Ons are dropped first. Normal playing, sustain management and `sendAllNotesOff()` (which spaces notes by 2 ms) are far below this.
- **Don't block waiting for BLE.** There is no "sent" callback by design.

### Packet format

Each notification is one BLE-MIDI packet: a header byte, then for each message a timestamp byte followed by the full message (no running status, which is the most compatible form). All messages in a packet share the timestamp of the moment the packet is built, in milliseconds, 13 bits.

A message costs its length plus one byte: 4 bytes for a CC or note, 3 for a Program Change. With the full 125-byte payload, a packet holds 31 CCs or notes. Before the host negotiates the MTU, the payload is 20 bytes: 4 messages per packet.

## Receiving Program Change

Packets written by the host are parsed in the NimBLE host task (Core 0). The parser handles running status, timestamps, MIDI clock and other real-time bytes, SysEx (skipped) and malformed or truncated packets without reading past the packet. A clock byte or a SysEx in the same packet as a Program Change doesn't hide the Program Change.

Program Changes go into an 8-entry queue. Read them with:

```cpp
uint8_t channel, program;  // channel 1-16
while (midiBLEReadProgramChange(&channel, &program)) {
  // switch config...
}
```

- It is non-blocking and returns false when nothing is pending.
- Call it from a Core 0 task (for example the WiFi or WebSocket task), **not** from the main loop or a BLE callback: switching config touches LittleFS and JSON, which is far too slow for the 400 Hz loop.
- If nobody reads the queue, the 9th Program Change onwards is dropped and counted as "dropped in".
- Only Program Change is forwarded today. To accept another message type, extend the filter in `MidiCharCallbacks::onWrite()` in `midiBLE.cpp`.

## Connection

| Setting | Value | Why |
|---|---|---|
| Device name | `PipoMotionBLE`, `PipoRangeBLE`, `PipoAnalogBLE` | Unchanged from before. In the scan response, because the 128-bit service UUID fills the advertisement. |
| Preferred ATT MTU | 128 | 125-byte packets: room for 31 messages while each packet still fits in one 256-byte NimBLE buffer. |
| Connection interval requested | 7.5 to 15 ms, latency 0, supervision timeout 3 s | Low latency. Android and Windows usually accept 7.5 ms. |
| Fallback | 15 ms / 15 ms, once, 3 s after connecting, if the interval is still above 15 ms | Apple hosts reject requests below their limits and keep the previous interval. 15/15 ms is within Apple's rules. |
| Security | Bonding allowed, no MITM, no Secure Connections; not required to connect | Same as the previous library. |
| Connections | One host at a time; advertising restarts when it disconnects | |

The interval the host actually chose is logged on connection and on every update.

**Upgrading from firmware with the old library:** NimBLE 2.x stores bonds in a different format. A host that had paired (bonded) with the Pipo may fail to reconnect until the Pipo is removed ("forget this device") in the host's Bluetooth settings and connected again. Hosts that only connected through a MIDI app without pairing are not affected.

## Memory

What this layer adds:

| Item | Size | Where |
|---|---|---|
| Outbound queue | about 300 bytes | static |
| Inbound queue (8 Program Changes) | about 100 bytes | static |
| `bleMidiTask` stack | 3 KB | heap, only when `BLEEnabled` |
| Per inbound write | one temporary copy of the packet (at most 125 bytes) | heap, freed immediately |
| Send path | nothing | no allocation |

**The NimBLE stack itself takes most of BLE's memory** (controller, host task, buffer pools). With the prebuilt Arduino 3.3 core, its settings come from the core's `sdkconfig.h`: all roles enabled, 3 connections, buffer pools of 12 × 256 and 24 × 320 bytes, host task stack 5 KB. They are defined unconditionally there, so `-D` build flags cannot change them. Reducing them (for example peripheral-only, 1 connection, smaller pools) needs a rebuild of the core libraries with `custom_sdkconfig`, like the `custom` environment in `platformio.ini` does.

**BLE controller memory:** Arduino 3.3 gives the BLE controller's RAM to the heap at boot unless a linked library opts in by including `esp32-hal-alloc-ble-mem.h`. If that happens, starting BLE corrupts the heap (`assert failed: block_locate_free ... tlsf_control_functions.h`). NimBLE-Arduino 2.5.x opts in by itself (through the core's `esp32-hal-bt-mem.h`); the old vendored NimBLE 1.4.1 didn't, which caused that crash.

## Diagnostics

`log_i` messages, all from the NimBLE host task:

| Message | Meaning |
|---|---|
| `MIDI BLE connected, interval X ms` | Host connected; interval it chose initially. |
| `MIDI BLE interval X ms, latency Y` | The host applied new connection parameters. |
| `MIDI BLE interval X units of 1.25 ms, requesting 15 ms` | The Apple fallback request was sent. |
| `MIDI BLE MTU X, packet payload Y` | MTU negotiated. |
| `MIDI BLE notifications on/off` | The host subscribed or unsubscribed. Sending only happens while on. |
| `MIDI BLE disconnected (reason 0x..)` then `BLE MIDI stats: ...` | Counters for the connection that just ended. |

The stats line:

| Counter | Meaning | If it's high |
|---|---|---|
| `packets` | Notifications sent | |
| `notify fails` | `notify()` returned an error; the batch was retried | Link or host problems |
| `busy ticks` | Intervals skipped because NimBLE's buffers were nearly full | Producing more than the link carries; values were coalesced meanwhile. Normal in bursts. |
| `dropped notes` | Notes or Program Changes dropped (FIFO full) | Note bursts too dense for the link |
| `dropped cc` | New controllers dropped (all 32 slots busy) | More than 32 distinct controllers in flight |
| `evicted note-on` | Note Ons evicted to queue a Note Off | Note bursts too dense for the link |
| `dropped in` | Program Changes received but not read in time | Nobody calls `midiBLEReadProgramChange()` |
| `task stack free` | Lowest free stack `bleMidiTask` has had since boot, in bytes | Below about 512: raise `kSenderStack` |

## Tuning

Constants at the top of `src/midi/midiBLE.cpp` and in `ble_midi_codec.h`:

| Constant | Default | Effect |
|---|---|---|
| `kBleMidiMaxPacket` | 125 | Packet payload cap; preferred MTU is this + 3 |
| `kItvlMin` / `kItvlMax` | 6 / 12 (7.5 / 15 ms) | Requested connection interval |
| `kAppleItvl`, `kFallbackAfterMs` | 12 (15 ms), 3000 ms | Fallback request and when it is checked |
| `kSupervisionTimeout` | 300 (3 s) | Link loss detection |
| `kMinFreeMbufs` | 8 | Buffer headroom kept for the host's own traffic |
| `kMaxPacketsPerTick` | 3 | Packets sent per interval when more is queued |
| `kOrderedCap`, `kLatestCap` | 32, 32 | Queue sizes |
| `kInQueueLen` | 8 | Program Changes waiting to be read |
| `kSenderStack` | 3072 | `bleMidiTask` stack |

## Limits

- **Order within a packet:** notes are sent before the controller values gathered in the same interval, so a CC and a note produced within the same 7.5 to 30 ms can arrive in the opposite order.
- **14-bit (hi-res) CC** is sent to USB only today. If it is added to BLE, the MSB/LSB pair must be kept together in `takeBatch()`; the round-robin can currently split them.
- **One host** at a time.
- **Timestamps** are per packet, not per message: timing inside one connection interval isn't preserved. BLE itself can't deliver it more precisely than one interval anyway.
- **Program Change only** on input today; see [Receiving Program Change](#receiving-program-change).
